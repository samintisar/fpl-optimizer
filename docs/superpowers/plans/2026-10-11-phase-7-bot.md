## Measured on botbox (2026-10-11)

Botbox has 4 cores, 3.8 GB RAM and no swap.

| Step | Wall time | Peak RSS |
|---|---|---|
| `fplopt build all` | 2 min 23 s | 1.7 GB |
| `optimize plan --entry 4570069 --gw 7 --xp v1 --no-chips` | 51 s (v1 fit + predict about 40 s; the 3 plans + roll in seconds) | 2.0 GB |

- **Only the live job runs the heavy steps.** Botbox can't run a build or a v1 run next to anything else that size. The live job runs them one after the other, with `build all` in a subprocess so its memory is freed before v1. The bot never runs either: it only reads contexts and solves (a few hundred MB), so no lock is needed. *(As built; the draft had a file lock.)*
- **v1 runs once per snapshot, not once per user.** Its xP frame is shared by every user; a user's plan is then the solve only (seconds).
- **Blocker: LightGBM needs the system library `libgomp1`, which botbox lacks.** The `fplopt` user has no sudo, so the user installs it: `sudo apt install libgomp1`. Everything else (`highspy`, `pulp`, `scipy`, `statsmodels`, `python-telegram-bot` 22.8) is already installed.

## Design

### 1. Plan context: v1 computed once per snapshot

`fplopt live prepare` builds the inputs every plan for the next deadline needs, from the newest bootstrap snapshot:

1. `build all` into `data/` on the server;
2. the view at the next deadline;
3. the v1 xP frame;
4. the player pool;
5. the season's `element_id` → `player_key` / web name;
6. GW → gw_index;
7. each past GW's deadline prices (what the entry import's `initial_prices` needs).

These go to `state/context/<season>-gw<gw>/<UTC>/`, as Parquet plus `meta.json`:
- season, GW, deadline;
- source bootstrap snapshot time and its sha256;
- git sha, model and optimizer spec;
- created_at.

The directory is written under a temporary name, then renamed, so a reader never sees a half-written context. The bot reads only contexts, never `data/`, so a rebuild can't race it.

It runs when the newest bootstrap snapshot is newer than the newest context's. That is after the 02:30 daily snapshot, after the tick's pre-deadline snapshot, and after the alert's own snapshot (§3).

### 2. User state (SQLite, `state/bot.sqlite`, WAL)

Tables per PLAN §3, keyed by `user_id`:
- `users`: `user_id`, `chat_id` (unique), `status` (`pending` / `active` / `blocked`), `created_at`.
- `user_settings`: `user_id`, `entry_id` (FPL team ID), `alerts` (on/off).
- `user_overrides`: `user_id`, season, GW, `free_transfers` (from `/setft`, for that GW only).
- `user_state`: per user and GW, the imported squad (`SquadSpec` as JSON), with the context it was planned on.
- `recommendations`: per user, GW and kind (`alert24`, `alert2`, `plan`):
  - the plans as JSON, the context id and the message text;
  - whether it was sent.

  This table plus the context directory is the live log of PLAN §8: plans, xP vectors, config, git sha and snapshot hash.

No usernames or other profile data are stored: only the chat id and the team ID.

### 3. Alerts: a 15-minute oneshot timer (`fplopt live tick`)

This runs as its own process rather than inside the bot. It exits and frees its memory, and it alerts on failure like the other jobs (`OnFailure=fplopt-failure@`). Each run:

1. **Context.** If a newer bootstrap exists, run `live prepare` (§1).
2. **24-hour alert.** From deadline − 24 h until the deadline, if a GW's `alert24` isn't recorded yet:
   - take a fresh FPL snapshot (bootstrap + fixtures, like the tick), so the flags are current;
   - prepare the context;
   - for each active user with alerts on, plan and send the full recommendation.

   A late start (box down, first deploy) still sends it, as long as it's before the deadline.
3. **Silent re-run.** From the tick's pre-deadline snapshot (the 2-hour window) until 30 min before the deadline:
   - re-plan on the fresh context;
   - send only if plan #1's moves for this GW, or the captain or vice, differ from what was sent. The message says what changed.
   - Either way, record it.

### 4. The bot (`fplopt bot run`, a long-polling systemd user service)

Built on python-telegram-bot. It uses the same `TELEGRAM_BOT_TOKEN` as the failure alerts; sending messages and polling don't conflict.

| Command | What it does |
|---|---|
| `/start` | Asks the admin for access (see *Access*); explains `/register` |
| `/register <team_id>` | Checks the team exists for this season (one entry-history call) and stores it; replies with the imported squad, bank, FTs and chips used |
| `/plan` | Imports the squad now (public API) and plans on the newest context. Replies with the recommendation, the context's snapshot time and the deadline |
| `/setft <n>` | Sets the free transfers for the coming GW (the reconstruction can be wrong) |
| `/alerts on\|off` | Turns the deadline alerts on or off |
| `/help` | Lists the commands |
| Admin: `/allow <chat_id>`, `/block <chat_id>`, `/users` | Manages access |

- **Command logic runs off the event loop** (`asyncio.to_thread`).
- **Updates are handled one at a time** (python-telegram-bot's default), so a second `/plan` waits for the first.
- **The solver** keeps the interactive 60 s wall-clock cap.

`/captain`, `/xp` and `/override` (PLAN §8) aren't needed for "done" and come after go-live.

### 5. Message format (phone-width, HTML `<pre>` only where aligned)

```
GW7 · deadline Sat 17 Oct 11:00 UK
Team 4570069 · £0.0m ITB · 4 FT · chips left: TC, BB, FH, WC2
xP from 03:49 UK (bootstrap 02:49)

Plan 1  (+1.5 xP over 6 GWs vs rolling)
 GW7  Rogers → Tavernier
      João Pedro → Gonzalo
 GW8  Groß → B.Fernandes, Slater → Mbeumo, Haaland → Thiago
 GW9  Hall → Mukiele
 …
 Captain Haaland · vice Saka
 XI  Kinsky; Silva, Calafiori, Konsa; Saka, Palmer, Tavernier, Groß; Haaland, Gonzalo, Wissa
 Bench  Verbruggen · Muharemović, Hall, Slater

Plan 2 (+1.2): GW7 Hall → Guéhi, João Pedro → Gonzalo
Plan 3 (+1.3): GW7 Hall → Guéhi, Rogers → Mbeumo, João Pedro → Gonzalo
Roll (save the FT): GW7 xP 54.8 vs 56.9

Plans 1–3 differ by less than the solver's gap: treat them as equally good.
Chips: none recommended (chips are your call for now).
```

Display rules:
- **Ties.** Plans whose objectives differ by less than the MIP gap are labelled as ties (PLAN §8 live finding).
- **Order.** Plans are shown ranked by objective (`planner.ranked`), because `optimize`'s solve order can be inverted within the gap. Alerts compare the top-ranked plan.
- **Detail.** Plan 1 shows its GW-by-GW moves; plans 2–3 and roll show only this GW's moves.
- **Notes.** The entry import's notes (e.g. "FTs inferred") are shown, as are any `/setft` override.

### 6. Access

**Invite-only (recommended).** A new chat's `/start` creates a `pending` user and messages the admin (`TELEGRAM_ADMIN_CHAT_ID`) with `/allow <chat_id>`. Until allowed, every command replies "waiting for access".

The admin chat is active from the start. This keeps the box's compute and the FPL API calls bounded, and nobody gets advice the system hasn't been tested on. PLAN §1 is "multi-user from day one, single user for now"; anyone the admin allows can use it.

### 7. Server layout and units

- `state/` (gitignored): holds `bot.sqlite` and `context/`.
  - `FPLOPT_STATE_DIR`, default `state`.
  - The 12 newest contexts are kept. The live log in SQLite is kept in full.
- `data/` on botbox: built by `live prepare` (botbox has no `data/` yet).
- New units in `deploy/systemd/`:
  - **`fplopt-bot.service`**: `Restart=on-failure`, `RestartSec=30`, a start-limit burst, and `OnFailure=fplopt-failure@`.
  - **`fplopt-live.service` / `.timer`**: every 15 min, offset to :05/:20/:35/:50 so it follows the archiver tick's snapshot. `TimeoutStartSec=20min`.
- Both wait for DNS like the others.
- `deploy/README.md` gets a *Bot* section: setup, `libgomp1`, enabling, `/allow`, and logs.
